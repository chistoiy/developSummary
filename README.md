# developSummary — 可复用的实现方案库

> 把"在某个项目里做过、验证过、值得再来一次"的设计与实现，
> 沉淀成**能直接照着做**的方案文档。
>
> 以后遇到同类需求：**查这里 → 引用对应文档 → 按验收清单逐条测**，
> 不用从头设计，也不用把踩过的坑再踩一遍。

---

## 1. 这是什么，给谁用

**不是**代码片段仓库，也**不是**某个项目的文档。它收录的是**跨项目可复用的方案**：
一个交互怎么做、一条链路怎么设计、一套流程怎么定，连同它们的**规则编号、实现骨架、
验收清单和已知坑**。

使用姿势：

- **自己/团队**：换项目再实现同类功能时，直接照抄规则与验收清单。
- **交给 AI**：把文档丢过去就能开工。每篇都含编号规则 + 骨架 + 可勾选验收项，
  AI 不需要反复追问"具体要什么"，也不会凭印象写一个似是而非的版本。
- **代码评审**：文档里的"已知坑"表可以直接当 checklist 用。

---

## 2. 怎么用（三步）

1. **找**：看下面的 [文档索引](#4-文档索引)，或按目录浏览。
2. **读**：直接打开，先看"标签/成熟度/适配成本"判断是否值得照搬。
3. **落地**：按文档里的「实现骨架」在你项目里实现，按「验收用例清单」逐条测。

### 引用方式（三种，按场景选）

| 方式 | 适合场景 |
|---|---|
| 贴链接 | 在需求/评审/对话里引用："按 developSummary 的 `mobile/flutter-gallery-drag-selection.md` 做" |
| 整篇复制到项目 `docs/` | 该方案会长期跟随这个项目演进；**改规则时记得回来同步 developSummary** |
| 复制 `TEMPLATE.md` 改写 | 要写的新方案和已有文档同类型，但细节不同 |

## 3. 目录结构

按**技术域**分一级目录，域内不再深层嵌套（扁平更好找）：

| 目录 | 收录内容 |
|---|---|
| `mobile/` | 移动端：Flutter / Android / iOS / Compose 的交互、组件与平台能力 |
| `web/` | 前端：页面/组件方案、状态管理约定、可视化 |
| `backend/` | 服务端：接口设计、数据模型、任务与队列 |
| `protocol/` | 协议与硬件通信：PTP、蓝牙、串口、USB 等（含逆向得来的结论） |
| `engineering/` | 工程流程：发布与版本管理、构建脚本约定、代码审查清单、发布公告模板 |
| `TEMPLATE.md` | 新文档的骨架，**新增一篇请复制它** |
| `README.md` | 本文件：导航 + 约定 |

> 一个方案跨多个域时，**按主要落点放**，在文档里用标签把其它域标出来。

## 5. 文档约定

### 命名

- **文件名**：英文 kebab-case（`flutter-gallery-drag-selection.md`）。
  中文标题会出现在文档 H1 里。理由：链接稳定、终端里好敲、跨平台不乱码。
- **标题**：中文，能一句话说清是什么。

### 每篇必备的六段

1. **元信息表** —— 标签、成熟度、来源项目、适配成本（让人 5 秒判断要不要看）。
2. **一句话定义** —— 说清这个方案是什么。
3. **编号规则** —— `R1 … Rn` / `D1 … Dn` 之类，**编号本身就是验收项**。
4. **实现骨架** —— 关键接口签名或伪代码，能直接照着写。
5. **验收用例清单** —— 可勾选的 `- [ ]` 列表，逐条测。
6. **已知坑** —— 现象 → 根因对照表。

> 规则必须写**为什么**（否则下次会被"顺手优化"掉）；
> 坑必须写**根因**（否则只会记住"这里有问题"，还是会再犯）。

## 7. 维护约定

- **developSummary 里的副本是权威版本**。项目里可以放副本，
  但改动规则时以这里为准（避免同一套规则在多个项目里分叉——这事已经发生过一次）。
- 文档里写具体文件路径/类名时，**注明来自哪个项目**，读者才知道要换成自己的。
- 结论类内容（尤其是逆向/实测得来的）要写**证据**，不能只写结论。
