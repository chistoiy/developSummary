# 性能优化前先定"物理上限"（可复用方法论）

| 项 | 值 |
|---|---|
| 标签 | `engineering` `性能` `方法论` `排查` |
| 成熟度 | ✅ 已落地（用它在一次"提速需求"上得出否定结论，避免了无效优化） |
| 来源项目 | NikonSync 的「无线下载提速研究」（`docs/无线下载提速研究.md`） |
| 参考实现 | 无代码，是一套判定流程 |
| 适配成本 | 零：换任何性能问题都能套 |

> 一句话：**先算出链路/资源的物理上限，再决定要不要优化。**
> 如果实测已经接近上限，那么任何软件层优化都是白费——该做的是换路径，不是改代码。

**适用场景**："能不能再快一点 / 再省一点 / 再并发一点"这类需求出现时；
也适用于评审别人的优化方案（先问上限是多少）。
**不适用场景**：已知是算法复杂度问题的场景（那时直接分析复杂度）。

---

## 1. 为什么要先定上限

优化是有成本的活动：改代码、引入风险、增加复杂度。
如果目标值本身就贴着天花板，这些成本花下去**收益为零**，而且会得出
"我已经优化了但还是不行"的错误结论，进而让人继续投入。

本项目的一次真实结论：

```
需求：无线下载照片能不能更快？
实测吞吐：1.5 ~ 2.4 MB/s
先算上限：链路协商速率 54 Mbps → 这是 802.11g 的满速
         → TCP 实际吞吐上限约 2.5 ~ 3.1 MB/s
结论：实测已达上限的 50% ~ 95% → 协议层没有可挖空间
行动：不再优化协议，改为换路径（5GHz / 数据线）
```

**如果没先算这一步**，会去做"调分块大小、加流水线、换重试策略"等一堆
收益为零的改动，并且每一样都要真机验证。

## 2. 方法步骤（编号即验收项）

- **M1 找一个能直接读到的"链路指标"**，而不是凭体感。
  例：Wi-Fi 的 `linkSpeed`（Mbps）、磁盘的顺序写带宽、CPU 核数、API 的官方限速。
- **M2 由指标推导理论上限**，并明确换算系数。
  例：802.11g 的 54 Mbps 是**空口速率**，TCP 实际吞吐要打约 5~6 折（前导、ACK、退避、重传）。
- **M3 把实测值与上限做定量比较**（算出百分比，不要只说"差不多"）。
- **M4 只有实测远低于上限（例如 <50%）时，才在软件层找原因**；
  此时按"离上限最远的那一层"优先排查。
- **M5 若已接近上限（>80%），改为换路径**：换频段、换传输方式、换存储介质、
  换协议版本、或者干脆改变需求（少传一点）。
- **M6 把结论与判据写下来**，包括"哪些方向已排除"——否则过几个月又会有人重新问一遍。

## 3. 推导物理上限时可用的现成判据

| 链路 | 指标 | 换算到应用层的经验值 |
|---|---|---|
| Wi-Fi 802.11g（54 Mbps） | 空口速率 | TCP 吞吐约 **2.5~3.1 MB/s** |
| Wi-Fi 802.11n 20MHz（65~72 Mbps） | 空口速率 | TCP 吞吐约 **4~6 MB/s** |
| Wi-Fi 802.11ac 5GHz（433 Mbps 单流） | 空口速率 | TCP 吞吐约 **20~35 MB/s** |
| USB 2.0 | 480 Mbps | 实际约 **25~35 MB/s** |
| 千兆以太网 | 1000 Mbps | TCP 吞吐约 **110 MB/s** |

> ⚠️ 这些是**数量级判据**，用来快速判断"有没有空间"，不是精确值。
> 场强、干扰、对端实现都会让实际值下移——所以还要看 M3 的百分比。

**一个很好用的反向判据**：802.11n 在 20MHz 下的速率集合是
6.5 / 13 / 19.5 / … / 65 / 72.2 Mbps，**里面没有 54**。
所以看到"协商速率 54 Mbps"就可以断定对端在按 **802.11g** 工作——
即使它的射频支持 n/ac，也不代表它在用。

## 4. 排查顺序（从上到下，找到第一个明显掉量的层就停）

1. **物理/链路层**：协商速率、频段、信号强度、干扰（含蓝牙共存）
2. **传输层**：TCP 窗口/缓冲、`TCP_NODELAY`、连接是否被中间件限速
3. **协议/应用层**：请求次数、往返次数、分块大小、是否串行化
4. **端侧处理**：写盘（FUSE/加密）、解码、GC、主线程阻塞
5. **业务层**：是否重复传输、传了本不需要的精度

> 每一层都要**给出数字**（该层的耗时或吞吐），而不是"应该没问题"。

## 5. 实现骨架（判定记录模板）

```
【链路指标】    <指标名> = <值>                    ← M1
【理论上限】    <推导过程与换算系数> → <上限值>      ← M2
【实测值】      <值>，样本 <n> 次，波动区间 <a~b>    ← M3
【占比】        实测 / 上限 = <百分比>
【结论】        □ 远离上限 → 在软件层优化，优先怀疑 <层>
               □ 接近上限 → 换路径：<备选路径>
【已排除】      1. …  2. …  3. …                    ← M6（必须写，防止重复研究）
```

## 6. 验收用例清单

- [ ] 拿出了一个**可直接读取**的链路指标，而不是"感觉慢"
- [ ] 上限有**换算依据**（引用了规格或公认经验值），不是拍脑袋
- [ ] 实测值与上限做了**百分比**比较
- [ ] 结论里明确了"优化 / 换路径"二者之一，并给出理由
- [ ] 把已排除的方向写进了文档（含为什么排除）
- [ ] 若结论是"换路径"，文档里写了具体的替代路径与预期量级
- [ ] 3 个月后有人再问同一问题时，能直接拿这份文档回答

## 7. 已知坑

| 现象 | 根因 |
|---|---|
| 优化做完没效果 | 没先定上限，实测本来就在天花板附近（M3 缺失） |
| "再调一版参数说不定就好了" | 把**波动**当成了可优化空间——要多次取样看区间，不看单次最好值 |
| 只说"慢"，说不出慢多少 | 没有量化指标（M1 缺失） |
| 换了更快的链路还是慢 | 瓶颈其实在对端的处理能力或读盘，不在链路；应回到第 4 节逐层给数字 |
| 半年后重复研究同一问题 | 没写"已排除"清单（M6） |
| 把理论 PHY 速率当成可用吞吐 | 忘了打折扣（M2）；54 Mbps ≠ 6.75 MB/s 可用 |

## 8. 复用清单

1. 下次遇到"能不能更快"时，先填第 5 节的模板，再决定动不动手。
2. 模板填完如果结论是"接近上限"，**把文档发给提需求的人**——
   这比"我优化了一下但还是不行"有用得多。
3. 把第 3 节的判据表按自己领域补充（加你的常见链路与经验换算值）。
