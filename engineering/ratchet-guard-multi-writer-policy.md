# 棘轮式守护用例在多写者下的维护口径（可复用）

| 项 | 值 |
|---|---|
| 标签 | `engineering` `测试` `守护` `协作` `CI` |
| 成熟度 | ✅ 已落地并验证 |
| 来源项目 | LifeHarness · `test/size_budget_test.dart`（大文件预算）、`test/catch_log_guard_test.dart`（静默 catch 登记）、`test/todo_trash_guard_test.dart`（软删谓词白名单）、`test/architecture_test.dart`（import 依赖规则）；本轮口径修正见提交 `7612d0c` 与 `docs/用例清理清单-20260930.md` |
| 参考实现 | 第 8 节的四类判定（over / grown / shrunk / stale）+ 一键重生成登记面 + 守护自证用例 |
| 适配成本 | 低中：每条「只许更严」的规则需要一张自己的登记表（baseline / 预算表 / 白名单） |

> 解决什么问题：仓库里加了棘轮守护（当前违规面登记成基线，之后只许收缩），
> 多人或多 AI 会话并行写同一仓库后，守护开始频繁报「我没动为什么红」，
> 于是大家学会给红灯找借口——守护整体失效。
> 不适用：安全/合规红线。那类「登记值变小」也必须红（应该用另一套只增不减的白名单）。

---

## 0. 一句话定义

棘轮守护的红灯语义**只保留「变坏」**，「变好」降级为带收敛动作的提醒；
同时用「扫描面下限断言 + 合成样本正对照 + 白名单失效检查」三件套防止守护悄悄空转。

## 1. 术语

| 术语 | 说明 |
|---|---|
| 登记面 / baseline | 一张表：`文件 → 当前允许存在的违规处数（或行数预算）` |
| over | 出现了未登记的违规 |
| grown | 已登记文件的违规数**上升** |
| shrunk | 已登记文件的违规数/行数**下降**（＝有人在改善） |
| stale | 登记项对应的文件已消失、或已降到预算线下却不删登记 |
| 空转 | 守护"全绿"但实际上一条都没扫到（解析器坏了/路径变了），最危险的假绿 |

## 2. 需求规则（编号即验收项）

- **R1 红灯只留给四类「变坏/失效」**：`over`、`grown`、`stale`、以及扫描面骤降（见 R4）。
- **R2 `shrunk` 不判红，打印提醒。** 为什么：别的会话把大文件拆小、把静默 catch 修好了，
  是**你希望发生的事**；判红等于惩罚改善，还会让多写者互相踩出无法解释的红灯。
  收紧登记值的动作由看到提醒的人顺手做，不做也不会漏新违规（`over`/`grown` 仍然拦得住）。
- **R3 提醒必须自带收敛动作**：给出重生成命令（如 `X_GUARD_DUMP=1 flutter test test/x_guard_test.dart`）
  或明确「把哪一行调小/删掉」。没有下一步的提醒等于噪音，一周后没人再看。
- **R4 守护要自证有效性**：断言「确实扫到了 N 个文件 / M 处」，N 设下限；
  再补一条**合成样本正对照**用例（已知哪些形态该放过、哪种该抓），钉住判定逻辑本身。
  解析器坏掉时最常见的表现是「零违规 = 全绿」。
- **R5 登记面可一键重生成且顺序稳定**（排序后输出），否则每次 dump 都在制造大面积 diff，
  并行会话之间互冲。
- **R6 白名单/豁免项必须带理由字符串，并检查理由是否仍成立**（文件还在吗？还命中规则吗？），
  失效即红。理由失效的白名单是最常见的"守护还在、实际已瞎"。
- **R7 扫源码的守护，扫描面必须覆盖同一逻辑库的全部分片**：Dart 的 `part of`、
  Kotlin 的多文件类、C++ 的头/实现。只扫"宿主文件"会让**拆文件这件事本身变成假红**。
  （本项目首拆即踩：锚只读宿主 → 拆出去的那半永远扫不到。）
- **R8 文本锚要按目标文件的真实行尾匹配。** 仓库里 CRLF 与 LF 混用时，
  脚本内 `str.replace(锚, 新)` 命中 0 次也静默成功；批量打补丁必须写「命中断言 + 体积校验」。
- **R9 一个事实只在一处钉。** 同一条文案/同一个约束被多个测试文件各钉一遍＝红灯放大
  （改一次红四处），会让别人把守护当成碍事的东西。锚要点在**稳定标识**上
  （`ValueKey`、枚举名、常量），而不是逐字中文标题。
- **R10 用例删除的判定标准 = 严格子集。** 只有「同一断言 + 同一被测路径 + 一处包含另一处全部前提」
  才可删。看着重复但前置状态不同（有无依赖注入覆写、是否走真实 I/O、是否在视口内）一律留。
  默认立场是**不删**，删的每一条都要能写出理由与被谁覆盖。
- **R11 合并用例只对纯函数成立**（同输入→同输出、无状态）。带 UI pump / 共享仓储的用例合并后
  前者会污染后者，还可能假绿；而表驱动化会让红灯输出从 N 行变 1 行，定位成本上升。
  **省 2 条用例不值这个价。**
- **R12 守护内部别重复遍历大目录**（同一棵树扫三遍要记忆化成一次共享），
  但要诚实记账：这类去重省的是 1~3 秒，**别按"提速"立项**，按"代码整洁/心智负担"立项。
  真正的耗时大头是每个测试文件各自的进程启动与编译。跨文件共享一次遍历通常**不划算**：
  各测试文件跑在独立 isolate，合不起来；硬合成一个巨型文件会制造多人写入热点 + 一处解析坏全灭。
- **R13 批跑失败先核文件名。** 传给测试器一个不存在的文件，常见表现是整批非零退出，
  极易被误读成「出现回归」。一片红先怀疑工装，不怀疑代码。

## 3. 数据模型

```
guard = { scanRoot, parse(文件) → 违规点集合, registry: {relPath → 允许处数} }
判定(registry, now):
  over   = now 有、registry 无                     → 红
  grown  = now[rel] > registry[rel]               → 红
  shrunk = now[rel] < registry[rel]               → 提醒（R2）+ 收敛指令（R3）
  stale  = registry 有、now 无（或已低于准入门槛）  → 红（空转风险）
  floor  = |now 扫描到的文件集| < 下限             → 红（R4）
```
不变式：**注册表里任何一项都必须"还在起作用"**；不起作用的项要么删要么红。

## 4. 关键流程（新增一条棘轮守护）

1. 定义「什么算变坏」，只有这些进 `expect`。
2. 扫一遍全仓，把当前违规面 dump 成登记表（顺序稳定），登记表随守护用例同文件存放，便于 review。
3. 写自证：扫描面下限断言 + 合成样本正/负对照。
4. 写白名单结构：`{路径: 理由}` + 理由失效检查。
5. 文档里写清「这条守护拦的是哪一类回潮」，否则第一个遇到红灯的人会选择放宽它。

## 7. 扩展点

- **E1** 同一套四类判定可覆盖：文件行数预算、静默异常登记、裸 SQL 谓词审计、
  禁用 API 调用点登记、i18n 硬编码文案登记。
- **E2** 登记值可以随时间自动收紧（如每次发版把预算下调 2%），但**必须是脚本改、不是人记**。
- **E3** 多写者场景可把提醒输出改成写入构建摘要/PR 评论，而不是控制台（更可能被看到）。

## 8. 实现骨架（Dart 测试形态，其它语言同构）

  for (final f in Directory('lib').listSync(recursive: true).whereType<File>()) {
    if (!f.path.endsWith('.dart')) continue;
    now[rel(f)] = f.readAsLinesSync().length;
  }
  final over = [...], grown = [...], shrunk = [...], stale = [...];

  expect(over, isEmpty, reason: '出现未登记的大文件：先拆分，或走治理评审后登记');
  expect(grown, isEmpty, reason: '已登记大文件长大了：预算只许减不许增');
  if (shrunk.isNotEmpty) {                  // R2：变好不判红
    // ignore: avoid_print
    print('[提醒] 以下文件已变小，请顺手调小登记值或删项：\n  ${shrunk.join('\n  ')}');

## 9. 验收用例清单

- [ ] 四类判定分开实现，只有 over/grown/stale + 扫描面下限会判红（R1/R2）
- [ ] 提醒文案里带重生成命令或"改哪一行"（R3）
- [ ] 有扫描面下限断言（R4）
- [ ] 有一份合成样本正对照用例，能抓到已知违规、放过已知合规（R4）
- [ ] dump 出来的登记表顺序稳定，重复 dump 不产生抖动 diff（R5）
- [ ] 白名单每项带理由，且有「理由失效检查」（R6）
- [ ] 源码锚覆盖全部分片文件（part / 多文件类），拆文件不假红（R7）
- [ ] 批量改源码的脚本有命中断言与体积校验（R8）
- [ ] 同一文案/约束没有在 3 个以上文件里被逐字重复钉（R9）
- [ ] 用例清理清单：每条被删的用例都写明了「被谁严格覆盖」（R10）
- [ ] 批跑脚本对不存在的文件名会显式报错，而不是整批非零退出（R13）

## 10. 已知坑

| 现象 | 根因 |
|---|---|
| 「我没改这个文件，门禁为什么红」 | 棘轮把 `shrunk` 也判红（违反 R2），别的会话的改善踩响了你的红灯 |
| 守护连续几周全绿，某天发现早就没在扫 | 解析器/路径变更 → 零命中 → 假绿；没有下限断言与正对照（违反 R4） |
| 把大文件拆成 part 之后源码锚红 | 只扫宿主文件（违反 R7） |
| 批量脚本"跑成功了"但什么都没改 | 锚与目标文件行尾（CRLF/LF）不一致，命中 0 次静默通过（违反 R8） |
| 改一次文案红四个文件 | 同一事实在多文件重复逐字钉（违反 R9） |
| 删掉「重复」用例后漏回归 | 两条的前置状态其实不同：有无依赖覆写 / 是否真实 I/O / 是否在视口内（违反 R10） |
| 表驱动合并后红灯只有一行，定位半天 | 合并把 N 条规则的失败挤进同一条（违反 R11） |
| 白名单越积越多、没人敢删 | 没有失效检查（违反 R6），删又怕漏，留着又没人看 |
| 为了"门禁提速"把 4 个守护合成 1 个巨型文件 | 各测试文件独立进程，共享不了遍历；换来写入热点 + 一处坏全灭（违反 R12） |
| 整批测试非零退出，被当成出现回归 | 传入了不存在的测试文件（违反 R13） |
| 登记项删不掉 | 没有 `stale` 判定与一键 dump（违反 R1/R5） |

## 11. 复用清单

1. 给每条「只能更严」的规则配一张登记表 + 一条 dump 命令，登记表与守护用例放同目录。
2. 判定拆成 `over / grown / shrunk / stale`，红灯只留前三类里的「变坏」与 `stale`。
3. 必配两条自证：扫描面下限 + 合成样本正对照；这是防假绿的唯一手段。
4. 团队约定成文：**提醒不判红，但提醒必须给收敛命令**；写进贡献文档，否则下一个人会重新争一遍。
5. 与 `engineering/module-decoupling-architecture-guard.md`（import 依赖规则）、
   `mobile/soft-delete-trash-source-guard.md`（谓词白名单）配合：那两篇是具体守护实例，本篇是它们的共同口径。
