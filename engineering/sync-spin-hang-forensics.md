# 同步空转 / 内存炸弹的取证与防护（可复用）

| 项 | 值 |
|---|---|
| 标签 | `engineering` `排查` `死循环` `内存` `测试` |
| 成熟度 | ✅ 已落地并验证 |
| 来源项目 | lifeHarness（`lib/features/calendar/presentation/widgets/time_pick_sheet.dart` 事故，2026-09-20） |
| 参考实现 | `test/architecture_test.dart` 规则 **R4**；护栏命令见 §8 |
| 适配成本 | 低（加一条静态守护规则 + 一份跑测脚本；无需改业务架构） |

> 用于「进程 CPU 满核 + 内存一路涨到 OOM + **超时参数杀不掉** + 不是死锁」这类故障：
> 同步空转（同步死循环）的**判据识别、带护栏取证、反向验证、编译期守护、调测资源护栏**。
>
> **不适用**：真正的死锁、异步竞态、`pumpAndSettle` 不收敛（那些会让出事件循环，超时/看门狗都能收）。
> 遇到"超时杀不掉"时先按本文排除同步空转，再回到死锁/异步方向。

---

## 0. 一句话定义

**同步空转 = 某个 isolate 在一个不让出事件循环的循环里空转**：它同时满足「CPU 打满单核」「内存单调涨」
「外部超时/信号杀不掉」「堆栈永远停在同一条语句」——因为定时器与信号处理都没有机会跑。

---

## 1. 术语

| 术语 | 说明 |
|---|---|
| 同步空转 | 同步执行的死循环，期间不 await/不 yield，事件循环停摆 |
| 自终止护栏 | 插在可疑点的计数器：超阈值即写日志（绝对路径）再抛错，用于把"无限"变成"有界可观测" |
| 夹逼定位 | 在函数内逐步打点（S0…Sn），用"最后一条成功的日志"确定失败语句 |
| 调测护栏 | 进程外的闸门：墙钟超时 + 峰值内存阈值，超了直接 kill 测试进程 |
| 空增量 | `for (init; cond; inc)` 里 `inc` 无副作用（如写成裸变量 `h` 而非 `h++`），条件恒真 |

---

## 2. 判据规则（编号即验收项）

- **R1** 先看"超时能不能收"。
  `--timeout` / `pytest-timeout` / 看门狗 **都杀不掉** ⇒ 该 isolate 不让出事件循环
  ⇒ **优先怀疑同步空转，不要先去查死锁或异步竞态**。
  （死锁会挂起线程但仍让出/停在锁等待，进程可被杀死；同步空转是"进程活着但像死了"。）
- **R2** CPU 表现：**单核 100%**（而不是全核），对应"单个 isolate 忙等"。
- **R3** 内存表现：**单调上升**且增长速率与循环体分配量成正比；不释放、不收敛。
- **R4** 崩溃信息里的分配量是线索，不是噪声。
  例如 `Exhausted heap space, trying to allocate 4294967312 bytes`（≈2³²+16）——
  按 `元素数 × 指针宽 + 头` 反推，容量已涨到 **约 2.7 亿**，直接证明"循环跑了非常久"，
  而不是"某一次分配特别大"。这能把排查从"哪行分配大"扭到"哪个循环不终止"。
- **R5** 崩溃栈里的行号可能因 **内联/行表** 偏移（collection-for 的 `List.add` 常被记到字面量末行）。
  所以行号只用于**夹逼区间**，不当作最终结论；必须用 R6 的方法确认到语句。
- **R6** 结论必须能**反向验证**：把可疑写法换成等价的安全写法（见 R9），故障立即消失 ⇒ 定位成立。
- **R7** 取证不许依赖 stdout。被挂死时 **输出缓冲不会 flush**，`print` 会全部丢失；
  一律 `File(<绝对路径>).writeAsStringSync(..., mode: append)`。
  注意测试进程的 CWD 未必是工程根，**必须绝对路径**。
- **R8** 护栏计数不要只插在 `build`。
  循环可能落在 `initState` / `layout` / 非 build 路径；护栏不触发不代表没有循环，要换点再插。
- **R9** 修复优先用**结构上不可表达**的写法：定长列表一律 `List.generate(n, (i) => ...)`
  （没有增量子句 ⇒ 空增量不可能出现）；其次才是手写循环并确保 `i++` / `i += n`。
- **R10** 加**编译期/静态守护**把这类 bug 变成可测项（见 §5）。

## 3. 状态机 / 数据模型

排查过程本身是个状态机，四步不可跳：

```
[症状] CPU 单核满 + 内存涨 + 超时杀不掉
   │
   ├─ R1 判定「不让出事件循环」 ──✗→ 回到死锁/异步方向
   │
   ▼
[收窄] 自终止护栏 + 逐步日志夹逼 → 得到「失败语句」（而不是"某行附近"）
   │
   ▼
[确认] 换成等价安全写法 → 故障消失 ⇒ 定位成立（R6）
   │
   ▼
[防复发] 静态守护规则 + 调测护栏（§5、§8）
```

不变式：**在拿到"失败语句"之前，不要动手改代码**——这类故障的直觉错率极高。

## 4. 关键算法或流程

### 4.1 自终止护栏（把无限变成有界）

```dart
final _probeF = File(r'<绝对路径>/_probe_trace.txt');   // 必须绝对路径（R7）
final _probeT0 = DateTime.now();
final Map<String, int> _n = {};
bool _fired = false;

void _tick(String tag) {
  final v = (_n[tag] = (_n[tag] ?? 0) + 1);
  final ms = DateTime.now().difference(_probeT0).inMilliseconds;
  if (v <= 3 || v % 2000 == 0) {                      // 低频采样，避免自身变成瓶颈
    _probeF.writeAsStringSync('$tag=$v t=${ms}ms\n', mode: FileMode.append);
  }
  if (v > 30000 && !_fired) {                         // 阈值到 → 存证 + 抛出
    _fired = true;
    _probeF.writeAsStringSync('=== LOOP @$tag v=$v all=$_n ===\n${StackTrace.current}\n',
        mode: FileMode.append);
    throw StateError('PROBE_LOOP $tag=$v');
  }
}
```

要点：**低频写**（否则插桩自己就把 IO 打满）、**到阈值先落盘再抛**（抛错信息可能被后续崩溃冲掉）。

### 4.2 逐步夹逼

在目标函数内按语句顺序打点，每步一个字母（`S0 enter` / `S1 …` / `S2 …`）。
日志停在 `S5` 而 `S6` 没出现 ⇒ 失败语句就是这两条之间那**一行**。
比"看栈里的行号"可靠得多（R5）。

### 4.3 反向验证

把可疑写法换成等价安全写法再跑一次：

```dart
// 可疑：[for (var h = 0; h < 24; h) ...]          ← 增量子句 h，空操作
// 安全：List.generate(24, (h) => ...)             ← 无增量子句
```

故障消失 ⇒ 定位成立。**这一步不能省**：它是"我猜的"与"我证明了"的分界。

### 4.4 静态守护规则（R4 的落地形态）

在架构守护测试里加一条：扫源码找 **增量子句无副作用** 的 `for`。

步骤（照抄即可）：

1. 先**剥掉字符串字面量与注释**（否则文案/注释里的 `for` 会误报）；
2. 匹配 `\bfor\s*\(`，按**括号配对**取出头部（支持跨行）；
3. 按**括号深度 0** 的 `;` 切成 3 段；段数 ≠ 3 的是 `for-in` / `for(;;)`，跳过；
4. 第 3 段 trim 后匹配 `^[A-Za-z_$][\w$]*$`（裸标识符）或 `^[0-9]+$`（字面量）⇒ **违规**；
5. 报出 `文件:行` + 修法建议。

误报率极低（合法的空增量写法基本不存在），漏报也低（这类 typo 就长这样）。

## 5. 与数据层的边界规则

- **D1** 取证日志写**工程外或临时目录**（绝对路径），别落进仓库；收尾时清掉。
- **D2** 调试用的插桩（写文件的探针、`dart:io` import、LayoutBuilder 计数）**不得进入提交**；
  修复后逐项移除，并用 `analyze` + 全量测试确认无残留引用。
- **D3** 静态守护规则只扫**业务源码目录**（如 `lib/`），不扫测试与生成产物。

---

## 6. 性能规则

- **P1** 护栏计数用**低频写盘**（1/2000 或首 3 次），否则插桩自身会成为新瓶颈并污染证据。
- **P2** 落地修复后测**两个量**：耗时与**峰值内存**。
  内存用运行时自带能力量（Dart `ProcessInfo.currentRss`；其它栈用 `getrusage` / `psutil`），
  别依赖 `tasklist`/`wmic` 这类在部分环境取不到数据的命令。
- **P3** 记录"修复前后"的同一指标作对照（本文场景实测：打开弹层 54s+→OOM，修后 <1s、增量内存 ~36MB）。

## 7. 扩展点

- **E1** 同一套"自终止护栏 + 夹逼"可直接用于：渲染层 layout 回环、Riverpod provider 互相触发、
  动画 ticker 自激、`setState` 在 build 内触发。
- **E2** 静态守护可扩展成通用 lint 集：空 `while` 体 + 条件不变、递归无终止条件、`for` 无增量。
- **E3** 调测护栏（§8）可抽成项目通用脚本，所有"可疑用例"统一走它。

## 8. 实现骨架

### 8.1 调测护栏（**跑任何可疑用例前先做这一步**）

超时参数对同步空转无效，必须在**进程外**设两道闸：

```bash
# 闸1：墙钟超时（80~120s）。--timeout 靠不住，用外部 timeout 兜。
HTTP_PROXY= HTTPS_PROXY= http_proxy= https_proxy= NO_PROXY='*' \
  timeout -k 5 90 flutter test test/suspect_test.dart --concurrency=1 --no-pub

# 闸2：另开一个看门狗，峰值内存超阈值即强杀测试进程（示例见 8.2）

# 收尾：确认无残留（残留会持续占内存/CPU）
<进程列表命令> | grep -i <测试进程名> || echo "无残留"
```

### 8.2 内存看门狗（Python，跨平台）

```python
import subprocess, time
LIMIT_MB, WALL_SECONDS, IMAGE = 1500, 85, 'flutter_tester.exe'
end, killed = time.time() + WALL_SECONDS, []
def procs():
    out = subprocess.run(['<proc-list-cmd>'], capture_output=True).stdout.decode('utf-8','replace')
    return [(pid, kb) for pid, kb in parse(out, IMAGE)]      # 各平台自行实现 enumerate
while time.time() < end:
    for pid, kb in procs():
        if kb > LIMIT_MB * 1024:
            subprocess.run(['<kill-cmd>', '/F', '/PID', pid], capture_output=True)
            killed.append(pid)
    time.sleep(0.3)
print(f'peak={max_kb/1024:.0f}MB killed={len(killed)}')
```

### 8.3 峰值内存自测（不依赖外部命令）

```dart
String mb() => '${(ProcessInfo.currentRss / 1024 / 1024).toStringAsFixed(1)}MB';
debugPrint('基线       = ${mb()}');
await tester.tap(find.text('open'));
await tester.pumpAndSettle();
debugPrint('打开弹层后 = ${mb()}');   // 与基线差值 = 该交互的内存代价
```

## 10. 已知坑

| 现象 | 根因 |
|---|---|
| 反复跑"疑似挂死"的用例，把开发机内存吃到满、系统卡死 | 超时参数对同步空转无效；每次试跑都是 GB 级代价。**跑之前先设 §8.1 护栏** |
| `print` 打的取证日志一条都没有 | 挂死时 stdout 缓冲不 flush（R7）。改用 `File.writeAsStringSync` 绝对路径 |
| 探针日志文件找不到 / 内容为空 | 写到了相对路径下，而测试进程 CWD 不是工程根（R7） |
| 崩溃栈指到的行"看起来完全无辜"（如某个 `padLeft`） | 内联/行表偏移：集合推导的 `List.add` 被记到字面量末行（R5）。用夹逼确认真实语句 |
| 护栏插在 `build` 里却从不触发，于是判定"没有循环" | 循环在 `initState` / layout / 非 build 路径（R8）。换点再插 |
| 判成死锁，越查越远 | 判据看错：死锁能被杀掉，同步空转杀不掉（R1） |
| 用 `tasklist` / `wmic` 量内存却全是 0 / 报错 | 部分环境（本地化 Windows、受限沙箱）取不到进程数据。改用运行时自带 API（P2/§8.3） |
| 静态守护规则"修完还是绿"，以为没问题 | 规则本身写错了（没剥字符串/注释、没按括号深度切分）。**必须用注入 bug 验证它会红** |

## 11. 复用清单

1. 遇到"CPU 单核满 + 内存涨 + 超时杀不掉"，先按 §2 R1 定性为**同步空转**，别去查死锁。
2. 照 §8.1 **先设调测护栏**（墙钟 + 内存阈值），再开始任何试跑。
3. 用 §4.1 自终止护栏 + §4.2 逐步夹逼拿到**失败语句**。
4. 用 §4.3 反向验证把"猜测"升级为"证明"。
5. 按 R9 改写法，按 R10 + §4.4 加静态守护，并**注入原 bug 验证守护会红**。
6. 按 §9 清单收尾（含清理插桩与探针日志）。
