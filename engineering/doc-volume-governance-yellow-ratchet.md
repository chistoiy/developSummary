> 解决「文档体量闸每轮都在喊要超、只能撞墙才救火」——把体量约束从**一条上限**升级成**三层机制**：写入预算与闸**同尺**、上限带**黄线预警**、上限随瘦身**自适应收紧**。
> 适用：任何「有一批反复被追加的文档 + 配套写入规则」的项目（尤其 AI 多会话接力的项目）。
> 不适用：文档量稳定、没有长期追加压力的项目（加了也无害，但收益低）。

---

## 0. 一句话定义

文档体量闸要成立，靠的不是「把上限调大」，而是三件事同时成立：**尺子统一**（写入预算与闸用同一量纲）、**红线之外有黄线**（到 90% 就预警，别等到 100% 才管）、**上限随瘦身自适应收紧**（棘轮，只降不升）——再按「规则型 / 堆积型」分类给出不同的治理动作。

## 1. 术语

| 术语 | 说明 |
|---|---|
| 红线（硬闸） | 超过上限即 lint 红灯、exit 1 |
| 黄线（软闸） | 上限 × 比例（默认 90%）触发**警告**，**不改 exit code**；到线须当轮瘦身或写明不瘦理由 |
| 写入预算 | 单次变更允许追加的量（**必须与闸同量纲**） |
| 棘轮 | 上限只降不升，放宽须人审并写理由 |
| 自适应棘轮 | 棘轮的加强版：每次瘦身后把上限收到「**瘦身后实测 × 系数**」 |
| 规则型件 | 内容即规则本体、每轮被注入的入口文件（如 `AGENTS.md`）——红线来自**注入余量**，不是历史堆积 |
| 堆积型件 | 内容按时间累积的状态源 / 台账 / 清单 / 计划书 |
| 滚动窗口 | 正文只留近 N 天（或「当前 + 上一枚」），更早整段沉 archive |
| 占用率 | 当前字节 / 上限——治理看板的一号读数 |

## 2. 需求规则（编号即验收项）

- **R1 尺子统一**：写入规则的**计量单位**必须与闸**完全一致**。闸数字节，写入预算就必须写字节；闸数行数，写入预算才写行数。**混尺的规则一律作废**。判定标准：规则里能读到「每批最多 N 字节」，且在闸里能找到同量纲的断言。
- **R2 红线（硬闸）**：每份受闸文档有明确上限（字节，或字节 + 行数双顶），超顶即 lint 红、exit 1。
- **R3 黄线（软闸）**：上限 × 90% 触发**警告文案**但不改退出码；收到黄灯的那一轮，收尾**必须**顺手动一次瘦身，或在变更日志里写明「本轮不瘦」的理由。黄线存在的意义＝把「撞墙才救火」变成「常态化小步瘦身」。
- **R4 自适应棘轮**：每次瘦身后把上限下调到「**瘦身后实测 × 1.15**」（系数可调，见 E1），**只降不升**；确实要放宽须人审、改常量并在注释里写理由。判定标准：上限常量旁能看到「自 X 降到 Y + 理由」。
- **R5 分类治理**：**规则型件**（入口）的红线是**注入余量**不是历史堆积 ⇒ **不设黄线**，加内容**必须净零改写**（同批删掉等量冗余）；**堆积型件**（状态源 / 台账 / 清单 / 计划书）适用黄线 + 棘轮。判据：这份文档「能不能靠删自己的历史来变短」——能＝堆积型，不能（删了就丢规则）＝规则型。
- **R6 闸要全覆盖**：凡「被人反复关注、会被长期追加」的文档都该有闸——不能只守入口三件套。**闸的覆盖是列举式的，写到哪守到哪**，新形成的热点文档默认无闸（本项目 `开发计划书.md` 就长期漏网，涨到 34 倍没人拦）。
- **R7 溢出走归档**：超限内容 `git mv` 进 `docs/archive/`，正文只留一行指针；archive **只进不出**，且不进死链扫描面。
- **R8 黄线也必须试跑**：黄线分支只在文档真到 90% 时才执行 ⇒ 天然是**死代码**。机制写完必须临时造一个 90% 的文件试跑一次，确认「打印警告且仍 PASS」。
- **R9 台账走滚动窗口**：状态源 / 台账类只留「当前 + 上一枚」；变更日志只留近 N 天，更早整段沉 archive。**时间窗口口径比条数口径更稳**（条数口径下「一枚」本身可能极长）。

## 3. 状态机 / 数据模型

单份文档的四个状态，及其**上限**的联动：

```
绿（占用 < 90%） ──追加内容──▶ 黄（90% ~ 100%）──继续追加──▶ 红（> 100%·lint 挂）
   ▲                                    │                              │
   │                              「当轮瘦身或写理由」                 │
   └──────── 瘦身 ◀──────────────────────┴──────────────────────────────┘
                └─▶ 同时把上限收到「瘦身后实测 × 1.15」（棘轮·只降不升）
```

不变式：
1. **上限单调不增**（棘轮）；每次下调都有注释来由。
2. 正文只留现行内容；历史一律在 archive（正文只留指针）。
3. 写入预算与闸**同量纲**（R1）——这是整个体系能自洽的前提。

## 4. 关键算法与流程

**4.1 这份文档该用哪套治理动作**（三分支）：

```
它是「每轮被注入的规则本体」吗？
 ├─ 是（规则型件） → 不设黄线；加内容走「净零改写」；红线＝注入余量
 └─ 否 ─┬─ 它是「按时间累积」的状态源/台账/清单/计划书吗？
        ├─ 是（堆积型件） → 黄线 + 自适应棘轮；台账走滚动窗口沉档
        └─ 否（一次性衍生件）→ 直接进 archive，不给闸（不进扫描面）
```

**4.2 黄线到线的当轮动作**：`瘦身` 或 `写明不瘦理由`——**二选一，不许沉默**。（沉默＝下轮直接撞红线。）

**4.3 瘦身后的棘轮动作**：`new_max = ceil(实测字节 × 1.15)`，写回常量并注释来由。项目实测：`STATUS 16384 → 14336`（瘦身后实测 12,304）、`交接文档 210 KiB → 168 KiB`。

## 5. 与数据层的边界规则

- **D1** 体量治理只动**文档、归档与校验脚本**，零代码 / 测试改动；全量测试基线不因治理轮重跑。
- **D2** 上限常量是**人审对象**，**写死在 lint 里 + 注释写理由**，不做成可自动读的配置项——否则「棘轮只降不升」会被顺手改大架空。
- **D3** 归档件（`docs/archive/`）不进死链扫描面（历史坐标允许失效），但**必须与正文用同一套相对路径**，保证正文里那行指针可达。

## 6. 性能规则

- **P1** 入口类文档每轮 prompt 都注入 ⇒ 它的字节上限**就是** token 成本上限。
- **P2** 黄线是零成本预警：正常路径（< 90%）不多做任何事，只在超线时多打印一行。
- **P3** 收益量化用三个数：**占用率**（当前 / 上限）、**距黄线字节数**、**累计棘轮下调量**。本项目一轮落地后六件占用率落在 84%～93%（入口按规则型豁免黄线）。

## 7. 扩展点

- **E1 棘轮系数**：默认 1.15。越小＝越紧（更勤瘦身、更快回访），越大＝越松（一次改动能塞更多）。
- **E2 黄线比例**：默认 90%。想更早介入可设 80%。
- **E3 多档黄线**：超长文档可用 80% / 90% / 95% 三档，对应「留意 / 当轮处理 / 禁止再追加」。
- **E4 双量纲闸**：字节 + 行数**两道都要**（行数预算挡不住「一行滚到几万字符」，只有字节闸拦得住）。

## 8. 实现骨架

```python
# lint 里的统一闸助手：红线 + 黄线一次判（黄线只收集，不改 exit code）
warn = []
def _gate(label, path, size, maxb, yellow=True):
    if size > maxb:
        red.append(f"{label}：{path} {size} 字节超上限 {maxb}（须归档瘦身）")
    elif yellow and size > maxb * 0.9:
        warn.append(f"{label}：{path} {size} 字节已达上限的 {size*100//maxb}%（黄线 90%）"
                    f"——收尾须顺手动一次瘦身，或在本批变更日志写明不瘦的理由")

# 常量集中 + 注释写来由（人审对象，勿做配置项）
AGENTS_BYTES_MAX  = 16384   # 规则型：红线＝注入余量的一半；不设黄线
STATUS_BYTES_MAX  = 14336   # 棘轮：16384 → 14336（瘦身后实测 12,304 × 1.15）
JIAOJIE_BYTES_MAX = 172032  # 棘轮：215,040 → 172,032（210 KiB → 168 KiB）
REQ_BYTES_MAX     = 174080  # 补的字节闸（原先只有行数闸＝尺子不齐）
PLAN_BYTES_MAX    = 71680   # 新补的闸：原先漏网的热点文档

# 输出：黄灯先行（只打印），红灯再决定 exit 1
for w in warn: print("体量黄灯：", w)
if red:  print("体量红灯：", *red, sep="\n"); sys.exit(1)

# 写入规则（与闸同量纲·R1）
#   变更日志：≤3 行 且 ≤400 字节 / 批      ← 行数是软约束，字节是硬约束
```

状态轮转脚本侧的同类闸（台账类）：

```python
MAX_FILE_BYTES = 14336      # 与 lint 的 STATUS_BYTES_MAX 同源，两处必须一起改
FIELD_BYTES_MAX = 400       # 「本批」正文 ≤400 字节；轮转：本批 → 上一批
```

## 9. 验收用例清单

- [ ] 每份受闸文档都能报出「当前字节 / 上限 / 占用率」三个数；**没有闸的热点文档已补上**（R6）。
- [ ] 写入规则里的量纲与闸一致——规则写「≤N 字节」，闸里就有字节断言（R1）。
- [ ] 变异：给受闸文档注水**超上限** → 红（exit 1）；还原 → 绿（R2）。
- [ ] 变异：给受闸文档注水到 **90%～100%** → **黄**（打印警告但 exit 0）；还原 → 绿（R3/R8）。
- [ ] 变异：给**规则型件**注水超上限 → 红；同批删等量冗余做净零改写后 → 绿（R5）。
- [ ] 每份瘦身过的文档，其上限常量已随之下调，且注释里写了来由（R4）。
- [ ] 溢出内容已 `git mv` 进 archive，正文只剩一行指针，死链扫描绿（R7）。
- [ ] 台账类正文只留「当前 + 上一枚」；变更日志只留近 N 天（R9）。
- [ ] 若黄线比例/棘轮系数被改过，能指出**谁审的、为什么**（D2）。

## 10. 已知坑

| 现象 | 根因 |
|---|---|
| 闸每轮都喊「要超」，永远只能在撞墙时救火 | **只有红线没有黄线**：不到 100% 就不管，到了已经来不及。红线是「不许越界」，黄线才是「常态瘦身」的抓手 |
| 写入规则写「≤3 行」，闸却天天红 | **两把尺子**：规则量**行数**、闸量**字节**。实测文档单行 600～1300 字符 ⇒ `≤3 行` 实际放行 **2.4 KB/批**，闸迟早红。规则与闸必须同量纲（R1） |
| 瘦身完的文件过一阵又长回上限 | 上限没跟着瘦身**收紧**（缺自适应棘轮）。「只减不增」若基线定在瘦身前，等于没瘦 |
| 给规则型入口也上黄线/棘轮，结果被逼着「删规则」 | 入口的红线是**注入余量**不是历史堆积 ⇒ 它该走「**净零改写**」（删冗余换新内容），不该被要求"瘦身"。两类件必须分开治（R5） |
| 黄线机制写好了，却从没被执行过 | 黄线分支只在文档**真到 90%** 时才跑 ⇒ 天然**死代码**。本项目就在「临时造 90% 试跑」这一次里抓出 `%（黄线 90%）` 未转义成 `%%` 导致的 format 崩溃——这类 bug 不试跑永远看不见（R8） |
| 只守了三件套，别的文档无声膨胀 | 闸的覆盖是**列举式**，写到哪守到哪；新形成的热点文档默认**无闸**。本项目 `开发计划书.md` 因此长期漏网（R6） |
| 台账文件按「只留当前 + 上一枚」裁完还很肥 | 条数口径下「**一枚**」本身可能极长（一次大事件一屏）。台账类应叠加**时间窗口**口径（只留近 N 天），并给单条也设字节预算（R9/R1） |
| 归档了内容，正文却出现死链 | archive 目录进了扫描面、或正文指针写了绝对路径。archive 应**不进**死链扫描，正文指针用与正文一致的相对路径（D3） |

## 11. 复用清单

1. **先量现状**：把每份「会被反复追加」的文档列出「当前字节 / 有没有上限 / 占用率」——**没上限的补齐**（R6）。
2. **统一尺子**：检查所有写入规则，把量纲改成与闸一致（太长的行数是软约束，字节才是硬约束）（R1）。
3. **加黄线**：所有堆积型件的闸都加一个「上限 × 90% → 警告」分支，只打印、不改退出码（R3）。
4. **瘦一轮再钉**：先真瘦一轮，然后按「瘦身后实测 × 1.15」把上限写回常量并注释来由（R4）。
5. **分类**：入口规则件豁免黄线、改走净零改写；堆积型件走黄线 + 棘轮；一次性件直接进 archive（R5）。
6. **台账上滚动窗口**：状态源只留「当前 + 上一枚」，日志类只留近 N 天，更早沉 archive（R9）。
7. **各造一次变异自证**：红线（注水超顶必红）、黄线（注水到 90% 必黄且仍 PASS）、净零（规则件加内容必须同批删等量）——**没被红过的闸等于没有**（R2/R3/R5/R8）。
8. **接进收尾门禁最前面**：黄灯在收尾时打印、红灯让后续步骤不跑（"红灯不起测试"）。
