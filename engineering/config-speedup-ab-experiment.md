# 配置类提速的同场景对照实验（可复用）

| 项 | 值 |
|---|---|
| 标签 | `engineering` `性能` `构建` `CI` `方法论` |
| 成熟度 | ✅ 已落地并验证 |
| 来源项目 | LifeHarness（Flutter + Android Gradle 8.14）· 实测记录 `docs/本机构建环境优化操作指导-20260930.md` 附 B/附 C |
| 参考实现 | 第 8 节实验脚本模板；落地物是 `android/gradle.properties` 里的两行开关 + 注释 |
| 适配成本 | 低（脚本与规则通用；**具体百分比必须自己重测**，不可照抄） |

> 解决什么问题：有人问「构建/流水线/打包能不能快一点」，于是往配置文件加了两个开关，
> 结果没人说得清快了多少、快在哪个开关上。这篇规定**怎么证明某个开关值多少**。
> 不适用：运行时性能优化（先用 `engineering/performance-ceiling-first.md` 判断还有没有上限空间）；
> 也不替代 CI 上的稳定基准测试——这里测的是「一次配置变更的归因」，不是「长期回归」。

---

## 0. 一句话定义

对配置开关做**只改一个变量、场景完全相同**的重复测量，把「提速」从体感变成可归因的百分比，
并把「首次成本 / 稳态成本」分开记账。

## 1. 术语

| 术语 | 说明 |
|---|---|
| 场景 | 目录形态（全新检出/全新工作树 vs 同目录增量）+ 产物是否 clean + 构建目标 + 并发度。**场景相同 = 除被测开关外全部一致** |
| 冷 / 暖 | 冷＝相关缓存（依赖、任务输出、语言服务器、杀软白名单）尚未建立；暖＝已被上一轮焐热 |
| 段行读数 | 构建器自己打印的分段耗时，例：`Running Gradle task 'assembleRelease'... 157.1s` |
| 对照组 | 所有待测开关全部关闭、其余与实验组逐字相同的那一轮 |
| 污染样本 | 测量期间被第三方负载（含测量者自己的磁盘遍历）拖慢的读数 |
| 首次成本 | 缓存类开关为了「喂缓存」额外付出的时间；只在第一轮出现 |

## 2. 实验规则（编号即验收项）

- **R1 先固定场景，再改开关。** 如果决策关心的是「发版出包要多久」，就必须按发版场景测
  （全新工作树 + 无产物）。同目录重复构建的数字对决策没有价值——它测的是增量缓存，不是你要优化的那条链路。
- **R2 一轮只改一个开关。** 其余条件（机器状态、目录形态、构建目标、并行会话数量）逐字相同。
- **R3 必须有一轮「全部开关关掉」的同场景对照组。** 没有它，任何差值都无法归因；
  拿另一个场景（比如主工作区 clean 构建）的数字当基线，几乎必然把别的因素记在开关头上。
- **R4 读数取构建器自己打的段行**，别只报总墙钟——总墙钟里混着依赖解析、工具启动、下载，
  而这些正是「和本次开关无关」的部分。段行读数要同时保留总墙钟作为旁证。
- **R5 计时期间，测量者自己不得在同一磁盘做任何遍历或写入。**
  `du -sh`、`find` 扫大目录、删旧产物、同时跑测试，全都算污染。**这是本方法最常见的失败模式**，
  而且它会伪装成「这个开关反而让构建变慢」的假结论。
- **R6 可疑样本先判污染，再判结论。** 比预期慢数倍的读数一律重跑干净轮；
  汇报里不要引用污染样本，非要提就明确标「勿作结论」。
- **R7 收益拆成首次成本与稳态成本两个数。** 缓存类开关第一轮通常更慢（要写缓存），命中才快；
  只测其中一轮会得出反方向的结论。至少跑：冷缓存轮 + 暖缓存轮 + 全关对照轮。
- **R8 落档时把「已排除的方向」一起写下来。** 例如「加杀软排除项、把缓存挪到数据盘，对冷构建耗时零收益」
  ——不写这条，过几个月一定有人重新问一遍、重新测一遍。
- **R9 开关本身进版本库。** 只写在本机用户目录的 `~/.gradle/gradle.properties` 里，
  别人、CI、新工作树都继承不到；要落到项目配置文件并附一行实测数据。

## 3. 状态机

```
设计轮次（列开关矩阵） → 跑一轮 → 读数
        ↑                          ↓
     采纳/不采纳 ← 判污染 ← 是否显著偏离预期
        ↑____________________↓（判污染则重跑该轮，别外推）
```

不变式：**任何一个被引用的数字，都必须能说出「它那一轮除了被测开关外，还和哪一轮完全相同」。**

## 4. 关键流程

1. 列出候选开关（例：`org.gradle.parallel`、`org.gradle.caching`、杀软排除、缓存目录迁移、镜像换站）。
2. 排轮次：**先全关对照**（而不是先跑「我以为会变快」那轮），再逐个开，最后测暖缓存命中。
3. 每轮之间**不要穿插磁盘整理**（R5）；如果必须改文件，改完就把那一轮视为新起点。
4. 读数汇总成一张表：`场景 / 开关组合 / 段行耗时 / 全程 / 备注`。
5. 结论写三行：主菜是谁、配菜收益多少、首次成本多少；再把开关提交进配置文件。

## 6. 性能规则（一条真实链路的现成量级，仅作"值不值得测"的参考）

被测工程：Flutter Android，20 核、Gradle 8.14，场景＝全新工作树从零出 `--split-per-abi` 三包。

| 开关组合 | 缓存状态 | 段行耗时 | 相对全关 |
|---|---|---|---|
| 只有 `jvmargs` | 冷 | 398.4 s | — |
| + `parallel=true` | 冷 | **157.1 s** | **−61%** ← 主菜 |
| + `caching=true` | build cache 空 | 182.6 s | −54%（首次喂缓存 **+25.5 s**） |
| + `caching=true` | build cache 命中 | **72.5 s** | **−82%**（同输入重出包） |

- **P1** 多核机器上 Gradle 默认串行跑任务图，`parallel` 往往是最大的单项收益，先测它。
- **P2** `caching` 类开关要按「命中率」估收益：改动越大命中越少，收益越接近首次成本（可能为负）。
- **P3** 杀软排除、缓存盘迁移这类「环境优化」对 CPU 密集的构建段通常**零收益**（同项目实测 −1.4 s/336 s），
  它们的真实收益在磁盘健康与高频小文件环节——**别把它们当提速立项**，否则一定失败。

## 7. 扩展点

- **E1** 把这套轮次模板搬到任何构建器（Gradle / Maven / CMake / npm / cargo）：只需替换 R4 的「段行关键字」。
- **E2** 若同一配置矩阵要长期看护，把轮次脚本挂进 CI 的 nightly，输出成趋势表。
- **E3** 缓存体积要设上限告警：`caching` 类开关会长期占盘（本项目 1 GB 量级），磁盘紧张时可整目录删除。

## 8. 实现骨架

```bash
#!/usr/bin/env bash
# 用法：改 write_props 的开关矩阵，每轮只动一个变量；全程不要再碰磁盘遍历。
set -u
PROPS=android/gradle.properties   # Windows 仓库若原文件是 CRLF，必须按 CRLF 写回，否则 git diff 变整文件改动
OUT=.tmp/_speed.txt

write_props() {                   # $1 = 开关组合名
  {
    printf 'org.gradle.jvmargs=-Xmx8G -XX:MaxMetaspaceSize=4G\r\n'
    printf 'android.useAndroidX=true\r\n'
    [ "$1" != base ]     && printf 'org.gradle.parallel=true\r\n'
    [ "$1" = both ]      && printf 'org.gradle.caching=true\r\n'
  } > "$PROPS"
}

run() {                           # 每轮都要 fresh 场景：新工作树或显式 clean
  local label="$1" t0 t1 out gl
  t0=$(date +%s)
  out=$(flutter build apk --release --split-per-abi 2>&1); rc=$?
  t1=$(date +%s)
  gl=$(printf '%s\n' "$out" | grep "Gradle task 'assembleRelease'" | tail -1 | tr -s ' ')
  echo "[$label] rc=$rc 全程=$((t1-t0))s :: $gl" >> "$OUT"   # R4：段行 + 全程一起记
}

# 轮次编排（R3 先对照，R7 冷/暖分开）
write_props base; run "全关对照";      rm -rf build
write_props par;  run "只开 parallel"; rm -rf build
write_props both; run "开缓存·冷";     rm -rf build
write_props both; run "开缓存·暖命中"
```

缓存类开关要「冷」的那轮，记得先把共享缓存目录清空（否则读到上一轮写的内容，测的就不是冷态）：

```bash
rm -rf "$GRADLE_USER_HOME/caches/build-cache-1"   # 纯可再生缓存，删了只影响下一轮的首次成本
```

## 9. 验收用例清单

- [ ] 有一轮「所有待测开关全关 + 同场景」的对照组（R3）
- [ ] 每轮相对上一轮**只改一个**变量（R2）
- [ ] 场景与决策关心的场景一致（发版就按全新工作树测，R1）
- [ ] 读数用构建器段行，并同时记录全程（R4）
- [ ] 计时期间测量者自己零磁盘遍历/零并发构建（R5）
- [ ] 异常样本被重跑而不是被引用（R6）
- [ ] 首次成本与稳态成本各有一个数（R7）
- [ ] 文档里写了「已排除方向」清单（R8）
- [ ] 开关进了版本库配置文件，并附一行实测数据（R9）

## 10. 已知坑

| 现象 | 根因 |
|---|---|
| 「开缓存后冷构建比全关慢 3 倍」 | 测量期间我并行跑了 `du` 遍历正在膨胀的 build 树（违反 R5）。重跑干净轮只慢 16%——**假结论差点被写进文档** |
| 把 `parallel` 的收益记成「依赖缓存焐热了」 | 没有同场景对照组（R3），借了另一场景的数字当基线 |
| 同目录重复构建测出 1 秒，以为提速成功 | 违反 R1：测的是增量缓存，不是发版链路 |
| 优化上线后 CI / 同事机器没变化 | 开关只写在本机用户目录（违反 R9） |
| Windows 挪了缓存盘，构建仍写旧目录 | 只做了 `robocopy` 拷贝、没设 `GRADLE_USER_HOME`。要用 `reg query` 复验环境变量，而不是问用户「设了吗」 |
| `robocopy` 报 error 123，日志里出现「文件: R:1 / W:1」 | 在 Git Bash(MSYS) 里跑，`/R:` `/W:` 被当成路径改写了。改在 cmd/PowerShell 跑，或 `MSYS_NO_PATHCONV=1` |
| 加了 Defender 排除项但耗时没动 | 第三方杀软接管时 Defender 处于 passive（`Get-MpComputerStatus` 报「无效命名空间」就是信号），排除要加在真正接管的那家 |
| 构建"成功"但产物是上一版 | 见 `engineering/flutter-android-release.md` R5b；它与此方法学正交，但同样会让耗时样本失真 |
| 改配置文件后 `git diff` 显示整文件重写 | 原文件是 CRLF，脚本按 LF 写回。写回时保持目标文件真实行尾 |
| 长任务用 `... \| tail` 看不到进度 | 管道缓冲；改成写文件 + 定期读状态端点/日志 |
| 本地 `origin/分支` 显示落后一大串 | 走了非常规 URL 推送（如 ssh-on-443）不回填跟踪引用；用 `git ls-remote` 定真相，别据此重复推 |

## 11. 复用清单

1. 复制第 8 节脚本，把「段行关键字」换成你自己构建器打印的那一行。
2. 轮次顺序按 **全关对照 → 单开关 → 缓存冷 → 缓存暖** 排，别从「我以为会变快」那轮开始。
3. 结论写两处：**配置文件里一行实测数**（让下一个改它的人知道为什么）+ **项目文档里的完整轮次表与已排除清单**。
4. 与 `engineering/performance-ceiling-first.md` 串起来用：那篇判断「还有没有空间」，这篇判断「这个开关值多少」。
