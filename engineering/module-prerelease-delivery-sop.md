# 大模块端到端交付 SOP + GitHub 预发布带 APK（可复用）

| 项 | 值 |
|---|---|
| 标签 | `engineering` `流程` `发布` `GitHub` `Flutter` |
| 成熟度 | ✅ 已落地并验证 |
| 来源项目 | LifeHarness（《开发计划书》§5.1/§7.1、《交接文档》铁律 6/7） |
| 参考实现 | `gh release create` 流程、release notes 四段结构、UI 确认门 |
| 适配成本 | 低（流程规范，命令通用；非 Flutter 项目替换构建步即可） |

> 一个模块从"需求"到"可安装的预发布包"的完整门序，含两道强制确认门（UI 原型确认、测试全绿）
> 与"漏发预发布=未交付"的交付定义。适用：单人/小团队 + 产品负责人深度验收的移动 App 项目。
> 不适用：多人并行大仓（需加 CODEOWNERS/合并门禁），或纯后端无 APK 形态（第 10 门换成镜像版本发布）。

---

## 0. 一句话定义

十道门（评审→设计→**原型确认门**→升版→计划→开发→测试→评审→推送→**预发布**），每道门有可勾选的产物标准，其中"UI 未经原型确认不得开发、模块未挂 prerelease+APK 不算交付"是硬闸。

## 1. 术语

| 术语 | 说明 |
|---|---|
| 确认门 | 必须由人（产品负责人）点头才能过的阶段闸口 |
| prerelease | GitHub 预发布版本，不算正式版本语义，可随意出包给体验者 |
| 四件套 | 需求清单 / 高保真原型 / 计划书 / 交接文档，任何变更同步更新 |

## 2. 需求规则（编号即验收项）

- **R1 UI 变更确认门**：任何涉及 UI 的需求调整，**先改高保真原型 → 用户浏览器验收并明确确认 → 才允许写业务代码**。*为什么：原型改一屏 5 分钟，代码改一屏 2 小时；视觉分歧必须留在低成本阶段。*
- **R2 需求即版本**：确认后需求文档升版 + append-only 变更日志；口头需求不落文档不开发。
- **R3 保真开发**：开发按已确认原型**逐元素**实现（文案/配色/布局/反馈/占位规范），禁止"先简化后补"。*为什么：待办模块首轮简化交付导致两轮返工，是这条规则的由来。*
- **R4 测试全绿门**：analyze 零告警 + 单测/守护测试全过 + 真机逐屏截图比对原型 + 受影响模块回归，四项缺一不算测完。
- **R5 独立评审**：AI 生成的代码要按"别人写的 PR"标准复审 diff，不轻信实现者的自我总结。
- **R6 预发布即交付定义**：**每完成一个大模块，推送分支后必须创建 GitHub prerelease**，notes 含功能描述+已知占位项，**并上传 debug APK 附件**；漏发视为该模块未交付。小修复不单独发版。*为什么：让产品负责人随时有一台能装的包，反馈周期从"等里程碑"缩到"当天"。*
- **R7 发布物与提交一致**：APK 从已推送的模块 HEAD 重新构建，禁止用旧构建产物充数。
- **R8 文档四件套同步**：每次第 9/10 门完成，交接文档进展表+变更日志同 commit 更新。

## 3. 状态机 / 数据模型

```
需求 → [门1评审] → [门2设计] → [门3原型确认✋] → [门4升版] → [门5计划]
    → [门6开发(TDD)] → [门7测试✋] → [门8评审] → [门9提交推送]
    → [门10 prerelease+APK]（大模块）/ 回 [门6]（缺陷修复轨道B: 6→7→9）
```

## 4. 关键算法或流程

**release notes 固定四段**（体验者视角）：
① 本版本内容（对齐原型的保真点清单 + 提交号）② 已具备能力 ③ 已知占位项（后续里程碑）④ 安装要求（系统版本/签名/离线说明）。

**tag 命名**：`v<语义版本>-<里程碑>.<模块名>`，如 `v0.1.0-m0.calendar`；APK 重命名 `app-<模块>-debug.apk` 上传后即删本地副本（`.gitignore` 排除 `*.apk` 防误提交）。

## 5. 与数据层的边界规则

- **D1** 门 2 若动表：DB version+1 + 迁移语句 + 迁移断言测试，与代码同 PR。
- **D2** 变更日志 append-only，新行一律加表尾；规则类变更（改流程）本身也要记一行。

## 6. 性能规则

- **P1** 轻量轨道 B（bug 修复）不强制门 1-5/10，但 UI 变动仍过门 3、动表仍补门 2——**规则按变更半径分级，不按工作量分级**。

## 7. 扩展点

- **E1** CI 化：push 触发 analyze+test+构建，prerelease 由 CI 上传（本地网络受限时先手工）。
- **E2** 分 ABI 出包减体积（见本仓库 `flutter-android-release.md`）。

## 8. 实现骨架

```bash
# 门9：提交推送（Conventional Commits；GitHub 间歇可达时加重试循环）
git add -A && git commit -m "feat(<模块>): <门序产出摘要>" && git push origin feat/x

# 门10：预发布 + APK
flutter build apk --debug                      # 从已推送 HEAD 重建
cp build/.../app-debug.apk app-x-debug.apk
gh release create v0.1.0-m0.x app-x-debug.apk \
  --prerelease --title "M0 预发布 · <模块>" --notes-file release-notes.md
rm app-x-debug.apk
```

## 9. 验收用例清单

- [ ] 涉及 UI 的需求：能找到"原型改动 → 用户确认"的对话/记录，且时间早于开发提交。
- [ ] 模块 PR 合入时测试四项全绿（R4 逐条）。
- [ ] GitHub Releases 页可见 prerelease：tag 指向模块提交、APK 附件可下载、notes 四段齐。
- [ ] 交接文档进展表与变更日志有对应行。
- [ ] 装机冒烟：新模块核心路径 + 上一模块回归各一遍。

## 10. 已知坑

| 现象 | 根因 |
|---|---|
| release 附了旧 APK，体验者说"和我说的不一样" | 构建发生在最后一轮修复之前（R7 由来）；发布前必须从已推送 commit 重建 |
| `gh release create` 成功但资产缺失 | 命令中途网络断；发布后回读 release 页面/`gh release view --json assets` 核验 |
| github.com:443 不通但 api.github.com 通 | 代理/防火墙按域名放行；git push 重试循环等待窗口，或改用 Contents API 提交文件 |
| 镜像站下载引擎产物 404 但直连可用 | 设置 `FLUTTER_STORAGE_BASE_URL` 后 gradle 走镜像路径 404：构建前临时移除该环境变量 |
| 流程写了没人遵守 | 规则没挂硬闸：门 3/门 4 靠"确认对话"留痕，门 7 靠测试命令，门 10 靠"漏发=未交付"的验收定义 |

## 11. 复用清单

1. 把 §2 十条规则贴进你项目的开发规范，标注哪两条是"人肉确认门"。
2. 写好 release notes 四段模板与 tag 命名约定。
3. 网络受限环境按坑表准备 push 重试 / Contents API 兜底。
4. 第一个模块跑完后复盘：哪道门形同虚设就删掉它，别养僵尸流程。
