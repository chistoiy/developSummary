# 陈旧红灯归位与死闸判定：欠跑的全量基线怎么收（可复用）

| 项 | 值 |
|---|---|
| 标签 | `engineering` `测试` `门禁` `回归基线` `变异测试` |
| 成熟度 | ✅ 已落地并验证（2354 例全量重跑·三条红灯全部归位·死闸两刀实测不红） |
| 来源项目 | LifeHarness（Flutter + sqflite）·`tools/run_gate.sh` / `tools/ftest.sh` / `test/*` |
| 参考实现 | 全量闸 `tools/run_gate.sh`（JSON reporter + 进度页）、批内增量 `tools/ftest.sh`、变异工装 `tmp/*_mutation.js`、守护 `test/trash_guard_test.dart` |
| 适配成本 | 低——流程与判定表可直接抄；需要项目有"两档门禁"与一条能单跑单文件测试的命令 |

> 一句话：两档门禁（批内只跑受影响文件／收口才跑全量）下，全量长期不跑会**攒出一批别人的陈旧红灯**，
> 在你这次收口时一次现形。本篇给：怎么把它们逐条定性（真红／假红／死闸／并发假红），怎么归位而不越权改别人的产品代码，
> 以及**怎么判断一条断言其实已经不咬人（死闸）**。
> **不适用**：只有一套 CI 全量闸的项目（不存在欠跑账）；把"改测试让流水线变绿"当默认手法的团队——本篇所有归位都以"产品代码一行未动"为前提。

---

## 0. 一句话定义

红灯归位＝先证明"这条红与我的改动无关"，再证明"它为什么红"，最后按四类定性各归各处；死闸判定＝把旧契约塞回代码，断言不红就说明它已经不再守任何东西，**删**，不要改写成永远为真的样子。

## 1. 术语

| 术语 | 说明 |
|---|---|
| 基线 | 上一次全量闸通过时的用例总数与状态（如"1855 绿·2026-10-04"） |
| 欠跑账 | 基线之后各批只跑增量，攒下未被全量验证的改动 |
| 归位 | 把红灯从"我这条批次的阻塞项"移交给"肇事批次的账"，并留下可复核结论 |
| 真红 | 产品行为与用例断言确实不一致（多为契约变更后用例没跟着改） |
| 假红 | 用例/装配/环境坏了，产品没问题（并发时序、夹具、路由缺失等） |
| 死闸 | 断言恒真：把它守的行为反向改掉，它也不红 |
| 变异自证 | 故意破坏被测代码，验证用例必须转红；用来区分"活闸"与"死闸" |

## 2. 需求规则（编号即验收项）

- **R1 两档门禁要写死在协作规范里**：批内只跑受影响文件；收口/发版才跑全量（全量独占、耗时长，禁止与其他会话并发跑）。
- **R2 欠跑要在账上**：STATUS/看板一栏固定写"全量基线＝N 绿（日期）·本批未重跑"。没有这行字，没人知道欠了多少。
- **R3 收口前补跑一次全量**：批次收口（或每 3~5 批）跑一次全量，把欠账结清；跑之前先确认没有并发测试进程（并发会撞原生库拷贝，表现为成片假红）。
- **R4 每条红灯必须逐条定性，不许"重跑一次绿了就当没有"**：定性四选一——真红（契约变更）／假红（装配或夹具）／并发假红（时序预算）／死闸（断言恒真）。
- **R5 归位以"产品代码一行未动"为前提**：能在测试侧修的（装配、路由表、等待预算、断言口径）一律测试侧改；确需改产品代码的，另立批次并挂归属。
- **R6 肇事提交要查出来并写进提交信息**：`git log -S '<断言文本>'` / `git log -L` / 对同一函数 `git log --oneline`，把"谁改了契约没改用例"钉死；否则下轮还会红。
- **R7 契约变更导致的真红＝改判或删除，二者都要留痕**：改判＝按现行契约重写断言；删除＝原位留注释说明"旧契约已作废、现行活判定在哪个文件哪一组"。**禁止**把断言改成恒真来"保留覆盖面"。
- **R8 死闸判定法**：改写后的断言必须做一次变异自证——把旧行为塞回被测代码，用例必须红；不红＝这条断言守的东西在代码路径上根本不可达（或被上游归一/短路），删。
- **R9 并发假红要登记不要硬改**：单跑绿、全量红＝时序预算在高负载下不够。登记（现象＋判据＋再犯的处理方案），别为了变绿把断言改弱。
- **R10 变异工装必须自净**：改前存原文/记 md5，跑完写回并**逐字节校验等于改前**，禁止用 `git checkout` 回退（会卷走同文件其他未提交改动）；工装自身报错（锚 0 命中、行尾不匹配）要显式区分"工装红"与"用例红"。
- **R11 基线数字要随用例增减记账**：删一条陈旧用例→基线 −1；新增常驻用例→下次全量应为 +1。写进状态文件，下次跑完全量对得上才算闭环。
- **R12 归位提交独立成枚**：不与功能批混在同一提交里，提交信息含"肇事提交 sha + 定性结论 + 产品代码零改动"。

## 3. 状态机 / 数据模型

一条红灯的处理状态：

```
全量现形 ──单跑复现?──┬─ 不红 ─→ 并发假红 ─→ 登记（R9）+ 观察阈值
                      └─ 仍红 ─→ 查肇事提交（R6）
                                   ├─ 断言守的是旧契约 ─→ 死闸检测（R8）
                                   │      ├─ 变异能红 ─→ 改判（按现行契约重写）
                                   │      └─ 变异不红 ─→ 删除 + 原位留注释指路
                                   └─ 装配/夹具问题 ─→ 测试侧归位（R5）
```

台账字段（状态文件里一行）：`基线数 · 跑批日期 · 红灯清单 · 每条定性与提交 sha · 新基线数`。

## 4. 关键算法或流程

**定性流程（每条红灯）**

1. 单跑该文件：`flutter test test/<file>.dart`（或项目的等价命令）。红→进 2；绿→判并发假红，进 5。
2. 读断言与产品代码：确认"现在代码实际给什么值"，别猜。
3. `git log -S '<断言关键串>' --oneline -- <test 文件>` 找最后一次改断言的提交；再用 `git log --oneline -- <被测文件>` 找改行为的提交。两者不一致＝典型"改了契约没改用例"。
4. 判性质：断言与现行**已拍板口径**冲突 → 真红（旧契约）；断言与现行口径一致而代码给了别的值 → 产品缺陷，另立批次。
5. 处理并做变异自证（R8），最后 md5 自净（R10）。

**死闸检测（本篇最有复用价值的一步）**

- 做法：把"旧契约"的实现塞回被测代码（一行 `copyWith(height: st.lineRatio!)` 之类），跑用例。
- 判读：红＝断言在守这条契约（活闸）；绿＝断言恒真。
- 恒真的常见成因：① 出口处有归一化函数把值覆盖掉（本篇实例：段落样式出口统一做行高归一，原书声明的 `lineRatio` 永远到不了 `height`）；② 断言读的是"被上游短路后的默认值"；③ 断言吃的是注释/文档字符串（守护类断言高发）；④ 类型系统或空安全使该分支不可达。
- 结论写法：删该用例，并在原位留注释——"旧契约已作废；现行活判定在 `test/xxx_test.dart` 的某组，它吃的是可达出口"。

**并发假红的判据**：首跑红 → 单跑绿 → 复跑全量绿；且用例里有真实等待预算（`runAsync + Future.delayed`、固定轮询次数×毫秒）。登记时把预算写进结论（"10×60ms 在高负载下不够"），并给再犯的处理方案（把等待挂到结果条件上，而不是加时长）。

## 5. 与数据层 / 仓库的边界规则

- **D1 归位不动产品代码**；若必须动，另立提交并在状态文件挂归属批次。
- **D2 并行会话共库**：只提交自己改过的文件（pathspec 级提交），别人在途文件只读；测试跑完删掉自己造的临时数据/夹具。
- **D3 回退用 md5 自净，不用 `git checkout --`**：后者会连带回退别人在同一文件里的未提交改动。
- **D4 全量闸独占**：跑全量前检查是否有并发测试进程；跑全量期间不再启增量测试（原生库拷贝冲突会制造成片假红，且耗时被拉长数倍）。

## 6. 性能规则

- **P1 先增量后全量**：批内跑受影响文件（秒级~分钟级），全量只在收口跑（本项目实测 2354 例 ≈ 5.5~10 分钟，视并发污染）。
- **P2 报耗时前先确认样本没被污染**：拿上一轮 elapsed 外推是错的；并发会话抢 CPU/IO 会把时长拉数倍。
- **P3 单文件单跑是定性主成本**：给测试命令加"只跑点名文件"的快路径（本项目 `tools/ftest.sh <files...>`，并过滤输出只留结果行）。

## 7. 扩展点

- **E1 自动归位报告**：把全量 JSON reporter 的失败项按"文件 → 最后改断言的提交 → 最后改被测代码的提交"三列生成表，人工只做定性。
- **E2 死闸扫描**：对高价值守护做周期性变异（CI 里跑一次变异子集），把"恒真断言"列入待删清单。
- **E3 基线漂移告警**：状态文件里记 `基线数`，全量跑完若 `实际数 ≠ 基线数 ± 本次用例增删` 就红——防"用例被静默跳过"。

// 变异工装最小形状（改前存原文 → 断言命中数 → 跑用例 → 写回 → md5 逐字节自净）
const before = fs.readFileSync(F);                       // Buffer：原样
const md5 = H(before);
let s = before.toString('utf8');
if (s.split(ANCHOR).length - 1 !== 1) fail('ANCHOR');    // 命中数断言
fs.writeFileSync(F, s.replace(ANCHOR, MUT_INSERT + ANCHOR), 'utf8');
runTests();                                              // 期望：目标用例红
fs.writeFileSync(F, s, 'utf8');                          // 复原
if (H(fs.readFileSync(F)) !== md5) fail('MD5');          // 自净校验（禁 git checkout）

## 9. 验收用例清单

- [ ] 1 每条红灯都有单跑结论（红/绿）与肇事提交 sha，写在提交信息与状态文件里。
- [ ] 2 归位提交里产品代码零改动（`git show --stat` 只有测试/文档）。
- [ ] 3 改判后的断言做过变异自证：把旧行为塞回去能红。
- [ ] 4 删除的用例在原位留了指路注释（现行活判定在哪个文件哪一组）。
- [ ] 5 并发假红有"单跑绿＋复跑绿"两条证据，且没被改弱。
- [ ] 6 新基线数与"旧基线 ± 本次用例增删"对得上。
- [ ] 7 变异工装自净：md5 等于改前，且与 HEAD 全等校验过。
- [ ] 8 全量跑期间无并发测试进程（时长与失败面正常）。

## 10. 已知坑

| 现象 | 根因 |
|---|---|
| 一片 FAIL，先怀疑产品炸了 | 多半是**工装红**（并发测试撞原生库拷贝、命令行没跑起来、输出被 grep 过滤掉）。先自证工装 |
| 全量首跑两条红，单跑都绿 | 并发时序预算不足（R9）。别改弱断言，登记＋给再犯处理方案 |
| 把 `wrap()` 全局换成带路由的装配后，另一条不相关用例红了 | 归位改动超出最小交叠面。只换需要的那几条用例的装配 |
| 页面落库改用 `pushReplacement('/x')` 后，测试里 `MaterialApp(home:)` 直挂炸 "No GoRouter found in context" | 产品代码引入了路由依赖而测试装配没有。归位＝补最小路由表（被测页挂 `/`，落点给桩） |
| 断言改成"等于用户设定值"后，两刀变异都不红 | **死闸**：出口处有归一化函数把该字段覆盖掉，旧契约在代码路径上已不可达。删用例＋留注释 |
| 守护摘掉代码行仍全绿 | 断言吃的是注释/文档里的同一个词（守护类高发）。改断代码行原文，并做变异自证 |
| 变异脚本"改前 md5"其实是在变异之后算的 | 工装自证假红（内容没问题、报 MD5 MISMATCH）。快照必须在改动前落盘，或写进独立文件供复原时读 |
| 用 `git checkout --` 复原变异 | 会连带回退同一文件里别人未提交的改动。改前存内存原文＋跑完写回＋md5 校验 |
| 拿上一轮全量耗时外推本轮 | 并发会话抢 CPU/IO 会把时长拉数倍；报耗时前先确认样本干净 |
| 改完用例忘了改状态文件的基线数 | 下轮全量对不上账，误判"用例被跳过"。R11 把基线数当一等公民 |
| 锚点用上一行的行首/下一行的行首 | Markdown 表格与 CRLF 文件里会吞掉相邻行或 0 命中。锚要取目标本身，且跟随目标文件行尾 |

## 11. 复用清单

1. 抄 §2 R1~R3＋R11：两档门禁 + 欠跑账 + 收口结清，这是让"陈旧红灯"不再砸到无辜批次头上的唯一办法。
2. 抄 §4 的**死闸检测法**（把旧契约塞回代码看断言红不红）——它把"要不要删这条用例"从争论变成实验。
3. 抄 §8 变异工装形状（命中数断言 + md5 自净 + 禁 checkout），任何需要"改源码跑一次再复原"的场合都能直接用。
4. 抄 §10 表当 code review checklist：一片红先怀疑工装、归位改动要最小交叠面、守护断言别吃注释。
5. 配套阅读：`engineering/mutation-harness-self-verification.md`（变异自证工装完整版）、`engineering/ratchet-guard-multi-writer-policy.md`（多写者下守护的红灯语义）、`engineering/agent-context-governance-lazy-loading.md`（状态文件/工单生命周期怎么承载这本账）。
