# 【高保真设计会话 → 开场白 → 开发会话的并行交接流程】（可复用）

| 项 | 值 |
|---|---|
| 标签 | `engineering` `流程` `AI协作` `原型` `交接` |
| 成熟度 | ✅ 已落地并验证 |
| 来源项目 | LifeHarness（`docs/开发计划书.md` §7.4；实例：记账模块 V1.32~V1.40 十轮、习惯打卡模块 V1.31） |
| 参考实现 | `prototype/index-ledger.html`（16 屏 + 14 弹层）、`docs/记账模块开发计划-20260923.md`（主文 + 九·补~九·补8）、`docs/需求清单.md` 模块 8 与第十节 |
| 适配成本 | 低（纯流程方案；需要项目允许"原型先行 + 文档四件套登记"的纪律） |

> 一句话：把「模块设计」和「模块编码」拆到**不同 AI 会话并行**推进，交接不靠复述对话，
> 靠**仓库文档 + 原型文件 + 一份固定模板的开场白**。设计会话结束时产出开场白，
> 用户把它粘给任意开发会话即可开工，全程零复述。
>
> 不适用：单人一次性「设计+实现」混做的项目（没有并行诉求，流程反而是负担）；
> 以及没有稳定文档纪律、原型即口述的项目——本方案的前提是"每轮验收都落档"。

---

## 0. 一句话定义

**设计会话产原型与修订记录，收口时生成「开场白」；开发会话按开场白的阅读清单自取上下文——文档是唯一交接载体，开场白只是索引。**

## 1. 术语

| 术语 | 说明 |
|---|---|
| 设计会话 | 单模块一个会话：复制主原型为模块副本，做高保真 UI + 细节需求，逐轮验收 |
| 验收轮 | 产品负责人带截图/指令来的一轮修订，对应需求清单一个 V 版本号 |
| 四件套 | 每轮验收的登记落点：需求清单（模块段+修订记录）、计划书修订节、交接日志行、项目记忆 |
| 开场白 | 设计收口时生成的开发会话启动指令（五段模板，见 §5） |
| 三源 | 需求清单（记录）/ 原型（事实源）/ 计划文档（口径）三份可能互相冲突的文档 |
| 变更单 | 模块原型对共享面（主 index.html 的 CSS/公共 JS）的改动清单，由唯一写者回灌 |

## 2. 需求规则（编号即验收项）

- **R1 设计会话每模块一个，原型只在副本定稿。** 从主原型复制 `prototype/index-<模块>.html`，模块屏的所有改动只发生在副本内；对共享面（全局样式、公共壳 JS）的改动记成**变更单**，由主原型的唯一写者统一回灌——否则多会话并行必撞车。
- **R2 每轮验收即时登记四件套，不攒批。** 需求清单加/改「V1.x 修订记录」条目 + 模块段落、计划书加「N·补k」修订节、交接文档变更日志加一行、项目记忆更新。修订记录必须写：来源指令、落地细节、校验结论、提交号。*为什么：跨会话交接只认仓库文档；攒批必漏（实测漏过一次模块段、一次整节，均因脚本无锚点断言静默失败）。*
- **R3 设计会话的提交一律本地，不 push。** push 是外发动作，每批收口单独向用户拿一句确认；开场白里必须列出「未 push 提交链清单」，防止开发会话换机器/换克隆时读不到设计成果。
- **R4 校验三件套每轮必跑并写进修订记录。** 静态（语法/跨脚本重名/清单清点）+ 无头浏览器逐屏断言（深链→DOM 断言→控制台零报错）；截图级像素验收留给产品负责人，文档中明示「留产品自查」，不假装做过。
- **R5 设计收口时产出开场白，且开场白内所有引用必须实查仓库核实。** 章节号、屏/弹层计数、提交号、文件路径一律当场 grep/ls 验证，禁止凭记忆写——*凭记忆写的章节号是开发会话最大的误导源。*
- **R6 三源冲突定序：需求清单修订记录 > 原型 > 计划文档。** 开场白中必须写明该顺序，并要求开发会话冲突时先向用户确认再动。
- **R7 开发会话按批次推进，每批交付后做保真走查再进下一批。** 批次拆解在计划书；逐元素操作表是走查依据；像素验收归人。

## 3. 会话生命周期（状态机）

```
[设计会话] 立项拍板(范围/深度) → 屏批实现+每批自检 → 验收轮×N(R2登记)
    → 收口(全部校验绿) → 生成开场白(R5) → 本地提交链清单(R3)
         ↓ 用户粘贴
[开发会话] 按开场白阅读清单加载 → 批k实现 → 增量校验(analyze+受影响测试)
    → 批间保真走查(R7) → 收口(全量+打包预发布) → push(需当次确认)
并行约束：设计会话A/B 与开发会话可同时运行，
    但共享面文件(主原型/需求清单同一段落)只允许一个写者，其余走变更单。
```

## 4. 关键流程

1. **设计期**：需求以「验收轮」为最小单元进版本链（V1.x → V1.x+1），每轮在需求清单头部与模块段双登记，保证开发会话从任一切口进入都能拼出全量口径。
2. **修订节写法**：计划文档正文保持初版结构，每轮验收追加「N·补k」节；**开场白必须注明「与正文冲突以补节为准」**——正文不改是历史，补节才是现状。
3. **版本漂移防护**：需求清单是全线共用的版本流水（本模块定稿在 V1.31，文件头可能已是 V1.40）。开场白里要写「本模块内容在 V1.31 段里，不要按文件头版本号找」。

## 5. 开场白五段骨架（实现模板）

```text
开发<模块>（技术栈），按仓库既有交接流程走，不要让我复述需求：

先读这 N 份，作为唯一依据（顺序即优先级）：
1. docs/<模块>开发计划-<日期>.md —— 落地口径主文：
   §x 屏幕清单 / §y 数据模型 / §z 逐元素操作逻辑总表（按它实现，不得自行增删入口）
   / 批次拆解 / 设置键表 / 测试
   **注意：「N·补 ~ N·补k」是 V<起>~V<止> 验收修订，与正文冲突一律以补节为准**
2. prototype/index-<模块>.html —— UI 唯一事实源（N 屏 + M 弹层），逐屏浏览器比对
3. docs/需求清单.md 模块 P 对应段 + 第十节 V<起>~V<止> 修订记录
   （清单现版 V<最新>，本模块内容在 V<定稿> 段里，不要按文件头版本号找）
4. <设计规格/组件规范等项目内引用>
5. docs/开发计划书.md <走查规程节> + <批次提速节>

硬约束：<DB 版本以代码实际值顺延（计划中序号仅相对）/ 模块特有口径逐条 /
全局 UI 规则（禁 emoji、禁教学文案…）/ 文件所有权（只动本模块与挂载点）/
新测试拆独立文件>

节奏：按批1开工（<内容>），每批交付后按逐元素表保真走查再进下一批；
批内只跑 analyze+受影响测试，收口跑全量+打包预发布；push 前先问我一句。
未 push 提交链：<设计会话全部本地提交号>
```

## 6. 验收用例清单

- [ ] 设计会话收口时，仓库内可 grep 到本模块每一轮的修订记录（数量 = 验收轮数）
- [ ] 开场白内每个章节号/文件路径/提交号，在新会话首次读取时全部命中（零虚构引用）
- [ ] 开场白含「补节优先」「版本漂移」「三源冲突序」三条免责声明
- [ ] 开发会话在**未与任何设计会话共享上下文**的情况下，仅凭开场白完成批1 且保真走查通过
- [ ] 并行两设计会话无共享面冲突（各自只改副本，变更单由唯一写者回灌）
- [ ] 未 push 提交链清单与实际 `git log` 一致

## 7. 已知坑

| 现象 | 根因 |
|---|---|
| 开发会话按计划书正文实现，做出来被验收打回 | 正文是初版历史，修订在「补节」里；开场白没写「补节优先」 |
| 开发会话翻需求清单找不到本模块条目 | 清单版本被其它模块线推进，本模块内容在旧版本段里（版本漂移）；开场白没注明定稿版本号 |
| 开场白引用的章节号/弹层数对不上 | 设计会话临期改动过结构，凭记忆写引用；违反 R5「实查仓库」 |
| 两个并行会话互改原型样式互相覆盖 | 共享面没有唯一写者；模块副本之外必须走变更单收口 |
| 开发会话换目录/换机器后读不到设计成果 | 设计提交全在本地（R3 纪律），开场白未列未 push 提交链，也没人提醒先 push |
| 批量文档登记脚本跑完发现三处漏登且无报错 | replace 锚点不唯一/不匹配时静默失败；登记脚本必须对每个锚点断言 `出现次数===1`，写盘前失败退出 |
| 交接后开发"顺手优化"掉某条交互口径 | 修订记录只写了 what 没写 why；规则不写为什么就会被当噪音清理 |
| 像素级差异到真机阶段才暴露 | 设计会话谎称做过视觉验收；R4 要求明示「截图级留产品负责人」 |

## 8. 复用清单

1. 在目标项目落一份流程条款（本项目为 `开发计划书 §7.4`），并立项目记忆/用户记忆各一条，保证跨会话可被检索。
2. 约定模块原型副本命名 `index-<模块>.html` 与共享面唯一写者，先建「变更单」通道再开并行。
3. 需求清单/计划文档采用「正文 + N·补k 修订节」双轨制，验收轮即时登记（R2），勿攒批。
4. 设计收口时按 §5 模板生成开场白，逐条实查引用（R5），把「补节优先 / 版本漂移 / 三源序」三句免责声明写死在模板里。
5. 开发会话开工第一步：按开场白清单通读 + `git log` 核对未 push 提交链，再动代码。
