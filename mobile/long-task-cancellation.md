# 长任务的取消（可复用）

| 项 | 值 |
|---|---|
| 标签 | `mobile` `交互` `架构` `取消` `Flutter + 原生` |
| 成熟度 | ✅ 已落地（含真机取消大文件的行为验证） |
| 来源项目 | NikonSync（下载取消：`PtpSession.requestCancelDownload()` + `CancelledException`） |
| 参考实现 | `PtpSession.kt` / `PtpUsbClient` / `PtpIpClient` / `NikonsyncPlugin` / `camera_gateway.dart` |
| 适配成本 | 中：需要执行层配合（取消点由它自己检查） |

> 一句话：**取消不是 UI 层的事**——执行层在阻塞循环里根本读不到 UI 的回调。
> 取消标志必须设在**跑循环那一侧**，并且"取消"要与"失败"彻底分开。

**适用场景**：任何"点一下取消但没反应"的长任务：大文件传输、批量操作、
长轮询、导出/压缩、设备固件升级、耗时计算。
**不适用场景**：毫秒级就能完成的操作（那时直接不执行即可）。

---

## 1. 术语

| 术语 | 说明 |
|---|---|
| **取消点** | 循环里检查取消标志的位置；应选在**可安全中断**的边界 |
| **取消异常** | 与业务失败区分开的类型（不要复用 `IOException`） |
| **半成品** | 中断时已写入的部分数据，必须清理 |
| **资源作废** | 中断后底层连接/通道不再可靠，需要重建 |

## 2. 规则（编号即验收项）

### 位置

- **R1** 取消标志必须设在**执行阻塞循环的一侧**（原生/后台线程/服务端循环内部），
  **不能只放在 UI 层**——UI 的回调传不进 `while` 循环。
- **R2** 取消点选在**块边界**（每次读取/处理一块之后），而不是每条数据一次
  （检查太频繁没意义，太稀疏则响应慢）。经验值：让取消响应在 **1 秒内**。
- **R3** 取消请求本身必须**即时送达**：不能与正在跑的任务排同一个队列
  （排在它后面就等于没取消）。

  > 例：Flutter 的 MethodChannel 调用若被派发到**同一个**后台线程池，
  > `cancelDownload` 会排在正在跑的下载之后 → 等文件传完才"取消"。
  > 应让取消走**主线程直通**分支。
  >
  > 相关：[单通道设备的请求调度](single-channel-request-scheduler.md)——
  > 若你的通道本来就是串行的，取消请求更要绕开它。

### 语义

- **R4** 取消用**独立异常类型**（如 `CancelledException`），
  **不要**复用 `IOException`/业务异常——否则会被现有的重试/降级逻辑当成失败处理。
- **R5** 取消**不可重试**：所有 `catch` 里都要先判取消再判失败，
  否则"取消"会变成"换个方式再跑一遍"（与用户意图完全相反）。
- **R6** 取消**不计入失败**：统计里要有独立的 `cancelled` 字段。
- **R7** 必须清理**半成品**（临时文件、已写入的流、未完成的目标文件）。

### 资源

- **R8** 中断后若通道处于**不可复用状态**（例如数据相位还剩一半没读），
  要显式作废并让下一次操作自动重建——**不能假装还能用**。
- **R9** 取消后 UI 要能继续用（可以立刻发起新的操作），不能卡在"取消中"。

### 呈现

- **R10** 文案要区分"已取消"与"失败"，并给出**剩余量**
  （例：`已取消（已下载 3，剩余 7 张未传）`）。
  把取消说成失败，用户会以为出了故障。

## 3. 实现骨架

```kotlin
// ① 执行层：取消标志 + 取消点（R1/R2）
class Transport {
  @Volatile private var cancelRequested = false
  fun requestCancelDownload() { cancelRequested = true }

  fun transfer(...) {
    while (hasMore) {
      if (cancelRequested) throw CancelledException("已收到取消请求（已收 ${done/1MB}MB）")
      readAndWriteOneBlock()
    }
  }
}

// ② 取消与失败彻底区分（R4/R5）
class CancelledException(message: String) : IOException(message)

fun download(...) {
  downloadInFlight = true
  try {
    transport.transfer(...)
  } catch (e: CancelledException) {
    // 不降级、不重试；清理后原样上抛
    deletePartial()
    throw e
  } finally { downloadInFlight = false }
}

// ③ 通道作废与自动重建（R8）
//    例：USB 传输取消后数据相位有残留 → 标记 needsReopen，
//        下一次事务先自动重连再执行
```

```dart
// ④ Dart 侧：识别取消（R6），并给可行动的文案（R10）
bool isCancelledError(Object e) =>
    e.toString().contains('已取消') || e.toString().contains('CancelledException');

// 批量任务里：取消后整批停下，且不计入 failed
} catch (e) {
  if (isCancelledError(e)) { summary.cancelled = true; break; }
  summary.failed++;
}
```

## 4. 边界情况

- **E1** 取消发生在**两个任务之间**：也应按同一套语义处理（停止后续、保留已完成）。
- **E2** 用户取消后**立刻发起新任务**：旧任务的清理不能影响新任务（用句柄/任务 id 区分）。
- **E3** 取消请求到达时任务**刚好完成**：应返回"已完成"而不是错误。
- **E4** 取消与失败**同时发生**（网络断了又点了取消）：优先按**失败**报告并说明，
  因为失败需要用户处理，而取消不需要。
- **E5** 批量任务的取消要**停止整批**，而不是只停当前这一项。

## 5. 验收用例清单

- [ ] 传一个大文件时点取消 → **1 秒内**停下（不是等整个文件传完）
- [ ] 取消后临时文件/半成品被删除，磁盘上没有残留
- [ ] 取消后 UI 显示"已取消"，**不是**"失败"
- [ ] 取消后统计里 `failed` 没有增加
- [ ] 取消后能立刻发起新的下载（不会被"正在取消"卡住）
- [ ] 取消不会被重试逻辑变成"再传一遍"（看日志只有一次传输）
- [ ] 批量任务中取消 → 后面的项不再继续传
- [ ] 取消后如果通道需要重建，下一次操作能自动完成（无需用户干预）
- [ ] 任务刚好完成时点取消 → 得到"已完成"而不是报错
- [ ] 断网同时点取消 → 报告为失败并说明原因（E4）

## 6. 已知坑

| 现象 | 根因 |
|---|---|
| **点了取消没反应，文件照样传完** | 取消标志只在 UI 层，进不了阻塞循环（R1）。这是最常见的一条 |
| 取消请求"排队"，等任务结束才生效 | 取消与任务共用了同一个串行队列（R3） |
| 取消后任务又自动跑了一遍 | 取消异常被当成普通失败，走了重试/降级分支（R4/R5） |
| 取消被计入失败数，用户以为出故障 | 统计没有独立的 `cancelled` 字段（R6） |
| 磁盘上留下损坏的半成品文件 | 没有在取消分支清理（R7） |
| 取消之后下一次操作读到脏数据/分配巨大内存 | 通道中断后残留在流里，却假装还能复用（R8） |
| UI 一直显示"取消中…" | 没有在 finally 里复位状态（R9） |
| 用户以为 App 坏了 | 文案把取消说成了失败（R10） |

## 7. 复用清单

1. 找出你那个长任务的**阻塞循环**在哪一层，取消标志就设在哪一层。
2. 定出取消点（块边界），目标响应 ≤1 秒。
3. 保证取消请求的**投递通道不排队**。
4. 定义独立的取消异常，并在**所有** catch 分支里优先判断它。
5. 取消路径上做三件事：删半成品、作废或复位资源、独立统计与文案。
6. 按第 5 节逐条验收——尤其是"1 秒内停下"和"不会被重试"这两条。
